# worker

Слой моделей над NATS JetStream. Задача приходит из рабочего стрима, результат уходит в `done.*`,
RPC `ai.rpc.*` получает ответ на `X-Reply-To`. Состояние задач держит JetStream, между рестартами
живёт только кэш весов в `/models`.

## Границы

- HTTP-сервера нет. Статус — core-subject `worker.status.<worker_id>` из контракта, здоровье
  контейнера проверяет `HEALTHCHECK` командой `python -m worker health`.
- Исходящий HTTP — только GET аудио по ссылке из задачи и вызовы LLM-провайдеров.
  `ai.rpc.complete` в сеть не ходит: отвечает только локальная модель.
  `fetch-models` ходит в сеть отдельной командой; в образе `HF_HUB_OFFLINE=1`.
- Нет PostgreSQL, Qdrant, S3. Вектор уезжает в `done.*`, в хранилища его пишет backend.
- Стримы и durable-консьюмеры создаёт jobs. Воркер подписывается только `pull_subscribe_bind`:
  `pull_subscribe` и `add_consumer` в `bus/` запрещены тестом `tests/unit/test_layers.py`.

## Контракт

`contract/worker-contract.json` — единственный источник лейнов, схем запросов и ответов, причин,
correlation-ключей и окон (`deadline_s`, `ack_wait_s`, `max_deliver`, задержки `nak`). В TOML этих
чисел нет. В образе файл лежит в `/app/contract/worker-contract.json`.

| Лейн | Стрим | Subject | Ответ | Публичная нода |
|---|---|---|---|---|
| `audio` | `INDEX_AUDIO` | `index.audio.new` | `done.index_audio` | да |
| `lyrics` | `EMBED_LYRICS` | `embed.lyrics.new` | `done.embed_lyrics` | да |
| `transcribe` | `TRANSCRIBE` | `transcribe.audio.new` | `done.transcribe` | да |
| `encode` | `ENCODE` | `encode.text.new` | `done.encode` | нет |
| `collab` | `TRAIN_COLLAB` | `train.collab.new` | `done.train_collab` | нет |
| `taste` | `TRAIN_TASTE` | `train.taste.new` | `done.train_taste` | нет |
| `ai` | `AI_RPC` | `ai.rpc.>` | ответ на `X-Reply-To` | нет |

## Конфигурация

Три слоя, каждый следующий перекрывает предыдущий:

1. `config/worker.toml` — все ключи с дефолтами;
2. `config/profiles/<WORKER_PROFILE>.toml`;
3. переменные `WORKER__<SECTION>__<KEY>`, например `WORKER__LANES__CAPACITY='{ audio = 8 }'`.

Неизвестный ключ — ошибка старта. Секреты задаются только ссылкой `"env:NAME"`:

| Переменная | Для чего |
|---|---|
| `WORKER_PROFILE` | имя профиля |
| `WORKER_NODE_NAME` | `worker.id`, попадает в `producer.worker_id` и subject статуса |
| `NATS_URL`, `NATS_USER`, `NATS_PASSWORD` | подключение к NATS |
| `ANTHROPIC_API_KEY` | основной LLM-провайдер |
| `LLM_FALLBACK_URL`, `LLM_FALLBACK_MODEL`, `LLM_FALLBACK_KEY` | запасной OpenAI-совместимый провайдер |

Провайдер LLM включён тогда и только тогда, когда его ключ непустой. Локальной модели ключи не
нужны: она загружается на каждом профиле, где включён лейн `ai`.

### Процессы и потоки

Каждый движок — отдельный процесс, вызов в нём идёт по одному. На `device = "cpu"` лейны
разнесены по процессам так, чтобы работали одновременно: `audio` (muq и mulan), `sep`,
`sync` (asr, align, mms), тренеры и `cpu-tools`. Модели грузятся по одной, чтобы пик памяти
при старте не складывался.

`runtime.isolate_encode = true` (профиль `cpu`) поднимает движок `encode` с `text` и текстовой
башней `mulan`; в `audio` остаётся только аудио-башня, копий нет. Аудио-проход поисковый запрос
больше не задерживает. `text` один и для `encode`, и для `lyrics`, а движок `encode` общий для
запросов `encode:lyrics` и `encode:mulan`. Приоритет решает супервизор, а не батчер: запрос, которому
нет свободного движка, встаёт в очередь срочных, массовые захваты этого движка ждут, пока она не
опустеет, а массовый вызов на нём прерывается между слоями модели и потом пересчитывается. Движок
сообщает о старте прерываемого вызова, и сигнал `SIGUSR1` уходит только после этого; захват, который
ещё не начал вызов, получает отказ `preempted` без обращения к движку. Батчер, ждущий движок под
массовый батч, при приходе срочной строки возвращает батч в очередь. Одна массовая строка
прерывается не больше 4 раз и не прерывается, когда до её дедлайна меньше двух прогнозов вызова;
строки, истёкшие после прерывания, считает `batch_rows_expired_after_preemption_total`.
`slots.text.replicas = 2` отдаёт `lyrics` вторую копию `text` (плюс ~3 ГБ).

Потоки (`runtime.threads`, `WORKER__RUNTIME__THREADS`):

- `0` (по умолчанию): бюджет `cpus - 1` делится поровну между движками, которые считают сейчас
  или закончили вызов меньше 30 с назад; число потоков задаётся при старте вызова и до его конца
  не меняется. Простаивающий тренер доли не берёт. Длинный вызов (`sep`, `asr`), начатый на
  пустой машине, держит весь бюджет, пока не закончится: в худшем случае на 8 vCPU сумма потоков
  доходит до ~2× бюджета (7 + 4 + 2 и 4 у запроса), это стоит части пропускной способности, но
  не останавливает работу;
- `N > 0`: каждому тяжёлому движку ровно `N` потоков;
- `cpu-tools` всегда 1 поток; поисковый запрос в `encode` — `min(4, cpus / 2)` поверх бюджета
  (он короткий), а `lyrics` в движке `encode` берут обычную долю;
- тяжёлые движки идут с `nice 10`, `encode` и `cpu-tools` — с `nice 0`, поэтому при полной
  загрузке ядро отдаётся запросу.

Распределение пишет строка `supervisor_start`. Пропускная способность — строка `lane_throughput`
раз в минуту и поля `per_hour`, `task_p50_ms`, `task_p95_ms` лейна в статусе.

Память: RSS движка пишут `engine_ready` и `slot_loaded` (`rss_mib`), раз в минуту строка
`engine_memory` (по движкам и `total_mib`), в статусе — `rss_mib` у слота. После загрузки и
после каждого вызова движок отдаёт свободную кучу системе (`malloc_trim`). Замер на CPU:
MuQ-MuLan целиком 3.4 ГБ, с одной башней 1.75 ГБ (из 1.7 ГБ разницы 0.66 ГБ уходят только
после `malloc_trim`), `text` (Qwen3-Embedding-0.6B) 2.9 ГБ, движок `encode` (`text` + текстовая
башня) 4.5 ГБ; без возврата кучи длинный текст поднимал его до 6.3 ГБ.

Профиль `cpu` на 8 vCPU / 23 ГБ при `mem_limit 21g` по оценке занимает 19–21 ГБ (`sync` ~9,
`encode` ~6, `audio` 4 + 2 на окна, `sep` ~2); на этой машине профиль не замерен. Локальная модель
в оценку не входит: ~1.5 ГБ, пока загружена, ~0.1 ГБ после 10 минут простоя. Порядок выкатки:
первый час смотреть `engine_memory.total_mib` и swap-in хоста (`vmstat 5`, столбец `si`). Если
`total_mib` выше 19 000 или `si` держится выше нуля дольше нескольких минут, снижать ёмкость по
шагам, каждый раз заново проверяя: `WORKER__LANES__CAPACITY='{ audio = 1, lyrics = 8,
transcribe = 2, encode = 16, collab = 1, taste = 1, ai = 16 }'`, затем `transcribe = 1`, затем
убрать `transcribe` из `WORKER__LANES__ENABLED`.

Разделение вокала получает половину оставшегося дедлайна задачи и останавливается между кусками
сам, без убийства процесса. Не успел — выравнивание идёт по миксу. Если по прошлым трекам видно,
что разделение не уложится, оно пропускается сразу. Прерванное разделение учит темп по реально
посчитанным кускам; каждый пропуск снижает темп на 5 %, так что трек, который не укладывается
вдвое, пробуется снова не раньше чем через ~14 пропусков.

`text`, `muq` и `mulan` тоже не убиваются по дедлайну вызова: модель проверяет время между слоями
или окнами и за секунду до дедлайна отвечает `expired`, строка уходит как `deadline_exceeded`,
а сторож движка ждёт ещё 15 с сверх дедлайна. Батчер учит секунды на единицу стоимости по прошлым
массовым вызовам и сразу возвращает строку, которой осталось меньше половины прогноза, вместо
того чтобы запускать её заведомо поздно.

### Локальная модель

`ai.rpc.complete` обслуживает слот `llm-local`: llama.cpp на CPU (GGUF, на GPU слои не уходят) на
всех профилях с лейном `ai`, torch в его движке не загружается. Цепочка провайдеров для
`resolve_artist` и `match_track` локальную модель не вызывает. Шаблон чата берётся из файла модели,
рассуждения выключены. Текст `system` и сообщений токенизируется без служебных токенов, поэтому
управляющий токен в реплике остаётся текстом. Ответ ограничен грамматикой из `schema` запроса, токен
выбирается жадно: тот же запрос даёт тот же ответ.

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `slots.llm-local.model`, `revision` | `unsloth/Qwen3.5-2B-GGUF` | репозиторий и коммит |
| `llm.local.file`, `sha256` | `Qwen3.5-2B-Q4_K_M.gguf` | файл весов и хэш, по которому его сверяет `fetch-models` |
| `llm.local.context_tokens` | 4096 | окно модели; промпт вместе с `max_tokens` длиннее окна — `invalid_request` |
| `llm.local.prompt_states` | 4 | сколько прочитанных префиксов промпта помнит движок |
| `llm.local.idle_unload_s` | 600 | простой, после которого веса выгружаются; `0` — как `runtime.idle_unload_s` |

Движок `llm-local` идёт с `nice 0` и `min(4, cpus / 2)` потоками, как поисковый запрос в `encode`.
Вызовы идут по одному. Пятый одновременный `complete` сразу получает `expired`
(`complete_rejected_total{why="busy"}`), чтобы очередь к модели не занимала лейн.

Основное время ответа — чтение промпта, поэтому движок хранит состояние модели после прочитанных
префиксов: конец `system`, конец последнего сообщения и общее начало двух разных `system` (находит
сам). Запрос с тем же началом читает только хвост. Вызывающему: `system` между запросами один байт
в байт, всё изменчивое — в сообщениях. Qwen3.5 — гибрид с рекуррентными слоями, обрезать его кэш по
позиции нельзя, зато состояние на ~1500 токенов занимает ~39 МБ (у обычного трансформера того же
размера ~130 МБ). Состояния конца `system` переживают выгрузку по простою, остальные с ней
удаляются.

Дедлайн: перед каждым куском промпта в 128 токенов и перед каждым токеном ответа движок сверяет
время с прогнозом шага и за секунду до дедлайна отвечает `expired`, процесс не убивается. Прочитанное
сохраняется, повтор того же запроса продолжает с этого места.

Ошибки: промпт не помещается в окно, `schema` не превращается в грамматику или шаблон отказал —
`invalid_request`; ответ оборван на `max_tokens` или не JSON-объект — `internal`
(`complete_rejected_total`); движок недоступен — `internal` (`complete_unavailable_total`). На
каждый ответ идёт строка `complete_answered` с `input_tokens`, `reused_tokens`, `output_tokens`.

Память движка `llm-local` с Qwen3.5-2B Q4_K_M: ~1.5 ГБ анонимной памяти и до 1.3 ГБ страниц файла
весов, которые ядро отдаёт под давлением; с четырьмя состояниями ~1.6 ГБ. После выгрузки по простою
остаётся ~0.1 ГБ.

Замер 2026-11-11: 4 потока, arm64-ВМ, сборка llama.cpp с dotprod, промпт персонажа ~1600 токенов
с 34 инструментами, ответ ~45 токенов. Машина делилась с другими задачами, числа — лучшие из
прогонов. «С нуля» — первый запрос с новым `system`, «повторный» — тот же `system` и новая
реплика. «Действия» — сколько из 15 реплик RU/EN дали ровно нужные команды, частично верные
считаются за половину.

| Файл | Чтение, ток/с | Ответ, ток/с | С нуля | Повторный | Память без страниц файла | Действия |
|---|---|---|---|---|---|---|
| Qwen3.5-0.8B Q4_K_M, 0.53 ГБ | 195–220 | ~50 | 8–9 с | 1.6 с | 0.7–0.9 ГБ | 10.5 |
| Qwen3.5-2B Q4_K_M, 1.28 ГБ | 80–93 | ~20 | 19–23 с | 4–5 с | 1.5–1.6 ГБ | 9.5 |
| Qwen3.5-4B Q4_K_M, 2.74 ГБ | 35–40 | ~10 | ~45 с | ~9 с | 3.0–3.4 ГБ | 15 |

Времена 4B пересчитаны из её скоростей: прогон упирался в память ВМ. 0.8B говорит по-русски
с ошибками и теряет составные просьбы. 2B говорит сносно, но в болтовне добавляет лишнюю команду.
Без ошибок действует только 4B. По умолчанию стоит 2B: в окно 30 с она укладывается с запасом,
а память хоста `cpu` под 4B не рассчитана. На x86 замера нет; на 8 общих vCPU (4 потока, AVX2)
ждать времён в 1.5–2.5 раза больше, то есть первый запрос 2B с новым `system` может один раз
вернуть `expired` и ответить на повторе.

`gpu-12*` и `gpu-16` работают с `trust = "public"`: непубличный по контракту лейн в `lanes.enabled` —
ошибка старта (`settings.check_public_lanes`), остальное ограничивают права ноды на брокере.
У них `idle_unload_s = 600` и батчи из `settings.SMALL_CARD_MAX_BATCH`, другой батч в профиле
попадает в `fallback_gaps`.

Откуда числа `gpu-16`. Веса в fp16/bf16: muq 0.67 ГБ, mulan 1.33, text 1.19, sep 0.46, asr 1.56,
align 1.84, mms 0.63, всего 7.7 ГБ. В режиме `slot` у каждой модели свой процесс и свой
CUDA-контекст (~0.45 ГБ), семь процессов: ~10.8 ГБ до первого вызова. `gpu-24` с тремя публичными
лейнами на 3090 (десять процессов, 11.5 ГБ весов) держит до ~20 ГБ, то есть вызовы поверх весов и
контекстов берут ~4 ГБ. Пик одного вызова вместе с весами ограничивают `tests/models`: sep с батчем 2
до 3 ГиБ, asr и align до 3 ГиБ, mms с батчем 8 до 2 ГиБ. У `gpu-16` батчи sep и mms вдвое меньше,
text 12000 против 16000, а transcribe с ёмкостью 2 держит не больше двух вызовов sep/asr/align/mms
сразу: обычно ~13 ГБ, по верхним границам тестов не выше ~15 ГБ. Пересоздание движка в режиме
`slot` на время держит две копии модели (у align +2.3 ГБ); если оно совпадёт с худшим пиком, ловит
`oom_unload`. muq 3 и mulan 6: трек даёт три окна по 30 с, это один и два трека за проход, память
они почти не двигают. На 12 ГБ после семи контекстов и весов на вызовы осталось бы ~2 ГБ, поэтому
`gpu-12` идёт в `lane`: два процесса вместо семи. Замер `gpu-16` 2026-10-15 на RTX 5060 Ti
(`:gpu-cuda13`, 9.8.19), 9 минут живой очереди: пик 12.9 ГБ, `slot_oom` ни одного, GPU 97%, процессы
~13 ГБ RAM; audio ~5.1 тыс., lyrics ~7.7 тыс., transcribe ~110 в час против 5.5 тыс., 8.3 тыс. и 280
у 3090 с `gpu-24` в то же окно. При OOM сначала `WORKER__LANES__CAPACITY='{ transcribe = 1 }'`.

Резервы включены во всех профилях: `align → mms`, `sep → mix`, регионный повтор, gap-fill,
`rescue_strategy = "global_ctc"`, `oom_unload`, запасной LLM-провайдер. Это держат тесты
`tests/unit/test_config_shipped.py` и `tests/contract/test_profiles.py`.

## Образ

Один `docker/Dockerfile`, сборка torch выбирается `FLAVOR`:

| Тег | `FLAVOR` | torch | Драйвер |
|---|---|---|---|
| `:gpu`, `:gpu-cuda12`, `:X.Y.Z-gpu` | `cu126` | 2.13, Pascal–Ada | ≥ R560 |
| `:gpu-cuda13`, `:X.Y.Z-gpu-cuda13` | `cu130` | 2.14, Turing+ и Blackwell | ≥ R580 |
| `:cpu`, `:X.Y.Z-cpu` | `cpu` | 2.13 | — |

`:gpu-cuda13` проверен 2026-10-15 на RTX 5060 Ti (sm_120, драйвер 595.84, CUDA 13.2), образ
9.8.19: models-тесты 47 passed, 3 skipped. Blackwell (sm_100, sm_120) идёт только на `:gpu-cuda13`,
Pascal и Volta (V100) остаются на `:gpu`. CUDA приезжает колёсами `nvidia-*`, драйвер — с хоста.
llama.cpp для локальной модели во всех трёх сборках один: колесо `llama-cpp-python` под CPU из
`uv.lock`; на x86_64 ему нужен процессор с AVX2, FMA, F16C и BMI2 (Haswell, Zen и новее).

```bash
docker build -f docker/Dockerfile --build-arg FLAVOR=cu126 -t worker:gpu .
podman build --format docker -f docker/Dockerfile --build-arg FLAVOR=cu126 -t worker:gpu .
```

`podman build` без `--format docker` молча выбрасывает `HEALTHCHECK`.

Контейнер: пользователь uid 10001, `read_only: true`, tmpfs `/tmp` и `/run/worker:mode=1777`, тома
`models:/models` и `work:/work`, `shm_size: 4g`, `stop_grace_period: 90s`, секреты через `env_file`,
один контейнер на GPU. Podman монтирует tmpfs без `mode` как `root 0755` (кроме `/tmp`), и воркер
не может записать `/run/worker/health.json`: процесс выходит с кодом 1 сразу после старта.

### Веса

Веса в образ не входят. Перед первым запуском:

```bash
docker compose run --rm -e HF_HUB_OFFLINE=0 worker fetch-models --profile gpu-24
```

Команда качает ревизии из конфига только для слотов включённых лейнов профиля (с резервами),
fastText `lid.176.bin`, чекпойнт сепаратора и GGUF локальной модели сверяет по sha256; GGUF с
другим хэшем удаляется. Код выхода: 0 — всё скачано,
1 — часть не скачалась (каждая ошибка в строке `model_fetch_failed`), 78 — ошибка конфига.
