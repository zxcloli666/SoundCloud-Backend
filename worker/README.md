# worker

Слой моделей над NATS JetStream. Задача приходит из рабочего стрима, результат уходит в `done.*`,
RPC `ai.rpc.*` и `speak.rpc.*` получают ответ на `X-Reply-To`. Состояние задач держит JetStream,
между рестартами живёт только кэш весов в `/models`.

## Границы

- HTTP-сервера нет. Статус — core-subject `worker.status.<worker_id>` из контракта, здоровье
  контейнера проверяет `HEALTHCHECK` командой `python -m worker health`.
- Исходящий HTTP — только GET аудио по ссылке из задачи и вызовы LLM-провайдеров.
  `ai.rpc.complete` в сеть не ходит: отвечает только локальная модель.
  `fetch-models` ходит в сеть отдельной командой; в образе `HF_HUB_OFFLINE=1`.
- Нет PostgreSQL, Qdrant, S3. Вектор уезжает в `done.*`, в хранилища его пишет backend.
- Стримы и durable-консьюмеры создаёт jobs. Воркер подписывается только `pull_subscribe_bind`:
  `pull_subscribe` и `add_consumer` в `bus/` запрещены тестом `tests/unit/test_layers.py`.

## Контракт

`contract/worker-contract.json` — единственный источник лейнов, схем запросов и ответов, причин,
correlation-ключей и окон (`deadline_s`, `ack_wait_s`, `max_deliver`, задержки `nak`). В TOML этих
чисел нет. В образе файл лежит в `/app/contract/worker-contract.json`.

| Лейн | Стрим | Subject | Ответ | Публичная нода |
|---|---|---|---|---|
| `audio` | `INDEX_AUDIO` | `index.audio.new` | `done.index_audio` | да |
| `lyrics` | `EMBED_LYRICS` | `embed.lyrics.new` | `done.embed_lyrics` | да |
| `transcribe` | `TRANSCRIBE` | `transcribe.audio.new` | `done.transcribe` | да |
| `encode` | `ENCODE` | `encode.text.new` | `done.encode` | нет |
| `collab` | `TRAIN_COLLAB` | `train.collab.new` | `done.train_collab` | нет |
| `taste` | `TRAIN_TASTE` | `train.taste.new` | `done.train_taste` | нет |
| `ai` | `AI_RPC` | `ai.rpc.>` | ответ на `X-Reply-To` | нет |
| `speak` | `SPEAK_RPC` | `speak.rpc.>` | ответ на `X-Reply-To` | да |

Лейн держит на сервере один pull-запрос на свои свободные места со сроком 5 с, без `no_wait` и
heartbeat, и отдаёт задачу обработчику сразу, как она пришла. Пустой запрос, закрытый раньше срока,
повторяется не раньше чем через секунду. Любой статус, кроме `408`, — ошибка: счётчик
`fetch_failures_total`, строка `fetch_failed` и пауза в секунду. Запрос, на который за 6 с не пришло
ни задачи, ни статуса, считается потерянным (`pull_unanswered_total`): лейн забирает уже пришедшее,
бросает старый inbox и подписывается на новый, чтобы опоздавший ответ не закрыл следующий запрос.

## Статус

Раз в 15 с воркер шлёт `worker.status.<worker_id>`. jobs отдаёт из него в Prometheus счётчики по
узлу (`node` равен `worker_id`):

| Метрика jobs | Поле статуса | Счётчик воркера |
|---|---|---|
| `jobs_worker_complete_answers_total{node}` | `counters.complete_answers` | `complete_answers_total` |
| `jobs_worker_complete_rejected_total{node,why}` | `counters.complete_rejected` | `complete_rejected_total{why}` |
| `jobs_worker_complete_unavailable_total{node,state}` | `counters.complete_unavailable` | `complete_unavailable_total{state}` |
| `jobs_worker_rpc_handed_on_total{node,method}` | `counters.rpc_handed_on` | `rpc_handed_on_total{method}` |
| `jobs_worker_rpc_expired_total{node,method}` | `counters.rpc_expired_by_method` | `rpc_expired_total{method}` |
| `jobs_worker_pull_unanswered_total{node,lane}` | `lanes.<lane>.pull_unanswered` | `pull_unanswered_total{lane}` |

Значение — итог воркера с его старта, как у `jobs_worker_done_total`: перезапуск воркера — сброс
счётчика, `rate` и `increase` его учитывают. Статус без этих полей принимается, итоги в нём нулевые.
Больше 16 значений `why`, `state` или `method` с одного узла jobs не отдаёт.

## Конфигурация

Три слоя, каждый следующий перекрывает предыдущий:

1. `config/worker.toml` — все ключи с дефолтами;
2. `config/profiles/<WORKER_PROFILE>.toml`;
3. переменные `WORKER__<SECTION>__<KEY>`, например `WORKER__LANES__CAPACITY='{ audio = 8 }'`.

Неизвестный ключ — ошибка старта. Секреты задаются только ссылкой `"env:NAME"`:

| Переменная | Для чего |
|---|---|
| `WORKER_PROFILE` | имя профиля |
| `WORKER_NODE_NAME` | `worker.id`, попадает в `producer.worker_id` и subject статуса |
| `NATS_URL`, `NATS_USER`, `NATS_PASSWORD` | подключение к NATS |
| `ANTHROPIC_API_KEY` | основной LLM-провайдер |
| `LLM_FALLBACK_URL`, `LLM_FALLBACK_MODEL`, `LLM_FALLBACK_KEY` | запасной OpenAI-совместимый провайдер |

Провайдер LLM включён тогда и только тогда, когда его ключ непустой. Локальной модели ключи не
нужны: она загружается на каждом профиле, где включён лейн `ai`.

### Процессы и потоки

Каждый движок — отдельный процесс, вызов в нём идёт по одному. На `device = "cpu"` лейны
разнесены по процессам так, чтобы работали одновременно: `audio` (muq и mulan), `sep`,
`sync` (asr, align, mms), тренеры и `cpu-tools`. Модели грузятся по одной, чтобы пик памяти
при старте не складывался.

`runtime.isolate_encode = true` (профиль `cpu`) поднимает движок `encode` с `text` и текстовой
башней `mulan`; в `audio` остаётся только аудио-башня, копий нет. Аудио-проход поисковый запрос
больше не задерживает. `text` один и для `encode`, и для `lyrics`, а движок `encode` общий для
запросов `encode:lyrics` и `encode:mulan`. Приоритет решает супервизор, а не батчер: запрос, которому
нет свободного движка, встаёт в очередь срочных, массовые захваты этого движка ждут, пока она не
опустеет, а массовый вызов на нём прерывается между слоями модели и потом пересчитывается. Движок
сообщает о старте прерываемого вызова, и сигнал `SIGUSR1` уходит только после этого; захват, который
ещё не начал вызов, получает отказ `preempted` без обращения к движку. Батчер, ждущий движок под
массовый батч, при приходе срочной строки возвращает батч в очередь. Одна массовая строка
прерывается не больше 4 раз и не прерывается, когда до её дедлайна меньше двух прогнозов вызова;
строки, истёкшие после прерывания, считает `batch_rows_expired_after_preemption_total`.
`slots.text.replicas = 2` отдаёт `lyrics` вторую копию `text` (плюс ~3 ГБ).

Потоки (`runtime.threads`, `WORKER__RUNTIME__THREADS`):

- `0` (по умолчанию): бюджет `cpus - 1` делится поровну между движками, которые считают сейчас
  или закончили вызов меньше 30 с назад; число потоков задаётся при старте вызова и до его конца
  не меняется. Простаивающий тренер доли не берёт. Длинный вызов (`sep`, `asr`), начатый на
  пустой машине, держит весь бюджет, пока не закончится: в худшем случае на 8 vCPU сумма потоков
  доходит до ~2× бюджета (7 + 4 + 2 и 4 у запроса), это стоит части пропускной способности, но
  не останавливает работу;
- `N > 0`: каждому тяжёлому движку ровно `N` потоков;
- `cpu-tools` всегда 1 поток; поисковый запрос в `encode` — `min(4, cpus / 2)` поверх бюджета
  (он короткий), а `lyrics` в движке `encode` берут обычную долю;
- `llm-local` берёт `llm.local.threads` из бюджета, пока идёт вызов: остальным достаётся
  `бюджет - threads`;
- тяжёлые движки идут с `nice 10`, `llm-local` — с `nice 5`, `encode` и `cpu-tools` — с `nice 0`,
  поэтому при полной загрузке ядро отдаётся запросу.

Распределение пишет строка `supervisor_start`. Пропускная способность — строка `lane_throughput`
раз в минуту и поля `per_hour`, `task_p50_ms`, `task_p95_ms` лейна в статусе.

Память движка с его дочерними процессами пишут `engine_ready`, `slot_loaded` и `slot_unloaded`
двумя числами: `resident_mib` (весь RSS вместе с отображёнными файлами весов) и `charged_mib`
(анонимная память и shmem; страницы файлов ядро может вытеснить, на лимит контейнера смотреть по
этому числу). Раз в минуту строка `engine_memory` даёт оба числа по движкам и суммы
`total_resident_mib`, `total_charged_mib`, в статусе те же поля у слота. После загрузки и
после каждого вызова движок отдаёт свободную кучу системе (`malloc_trim`). Замер на CPU:
MuQ-MuLan целиком 3.4 ГБ, с одной башней 1.75 ГБ (из 1.7 ГБ разницы 0.66 ГБ уходят только
после `malloc_trim`), `text` (Qwen3-Embedding-0.6B) 2.9 ГБ, движок `encode` (`text` + текстовая
башня) 4.5 ГБ; без возврата кучи длинный текст поднимал его до 6.3 ГБ.

Профиль `cpu` на 8 vCPU / 23 ГБ при `mem_limit 21g` по оценке занимает 19–21 ГБ (`sync` ~9,
`encode` ~6, `audio` 4 + 2 на окна, `sep` ~2); на этой машине профиль не замерен. Локальная модель
в оценку не входит: пока загружена, ~0.35 ГБ анонимной памяти, ~1.24 ГБ страниц весов и до
`llm.local.state_cache_mib` состояний; после 10 минут простоя ~70 МБ и префиксы `system`; без неё
`[llm.local] enabled = false`. Порядок выкатки: первый час смотреть
`engine_memory.total_charged_mib` и swap-in хоста (`vmstat 5`, столбец `si`). Если
`total_charged_mib` выше 19 000 или `si` держится выше нуля
дольше нескольких минут, снижать ёмкость по шагам, каждый раз заново проверяя:
`WORKER__LANES__CAPACITY='{ audio = 1, lyrics = 8,
transcribe = 2, encode = 16, collab = 1, taste = 1, ai = 16 }'`, затем `transcribe = 1`, затем
убрать `transcribe` из `WORKER__LANES__ENABLED`.

Разделение вокала получает половину оставшегося дедлайна задачи и останавливается между кусками
сам, без убийства процесса. Не успел — выравнивание идёт по миксу. Если по прошлым трекам видно,
что разделение не уложится, оно пропускается сразу. Прерванное разделение учит темп по реально
посчитанным кускам; каждый пропуск снижает темп на 5 %, так что трек, который не укладывается
вдвое, пробуется снова не раньше чем через ~14 пропусков.

`text`, `muq` и `mulan` тоже не убиваются по дедлайну вызова: модель проверяет время между слоями
или окнами и за секунду до дедлайна отвечает `expired`, строка уходит как `deadline_exceeded`,
а сторож движка ждёт ещё 15 с сверх дедлайна. Батчер учит секунды на единицу стоимости по прошлым
массовым вызовам и сразу возвращает строку, которой осталось меньше половины прогноза, вместо
того чтобы запускать её заведомо поздно.

### Локальная модель

`ai.rpc.complete` обслуживает слот `llm-local`: llama.cpp на CPU (GGUF, на GPU слои не уходят) на
всех профилях с лейном `ai`, torch в его движке не загружается. Цепочка провайдеров для
`resolve_artist` и `match_track` локальную модель не вызывает. Шаблон чата берётся из файла модели,
рассуждения выключены. Текст `system` и сообщений токенизируется без служебных токенов, поэтому
управляющий токен в реплике остаётся текстом. Ответ ограничен грамматикой из `schema` запроса, токен
выбирается жадно: тот же запрос даёт тот же ответ.

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `llm.local.enabled` | `true` | `false` — движок не стартует, веса не нужны, `complete` уходит другому воркеру |
| `slots.llm-local.model`, `revision` | `unsloth/Qwen3.5-2B-GGUF` | репозиторий и коммит |
| `llm.local.file`, `sha256` | `Qwen3.5-2B-Q4_K_M.gguf` | файл весов и хэш, по которому его сверяет `fetch-models` |
| `llm.local.context_tokens` | 8192 | окно модели; промпт вместе с `max_tokens` длиннее окна — `invalid_request` |
| `llm.local.eval_chunk_tokens` | 128 | кусок промпта за один проход; между кусками движок сверяет дедлайн |
| `llm.local.state_cache_mib` | 256 | память под прочитанные префиксы промпта |
| `llm.local.idle_unload_s` | 600 | простой, после которого веса выгружаются; `0` — как `runtime.idle_unload_s` |
| `llm.local.threads` | 2 | потоки llama.cpp, не больше бюджета CPU; с длинным `system` на 8+ vCPU — 4 |
| `llm.local.nice` | 5 | приоритет процесса движка |
| `llm.local.max_in_flight` | 2 | сколько `complete` ждут модель одновременно, включая идущий |

Перед стартом воркер сверяет флаги CPU с теми, под которые собран llama.cpp из колеса (x86_64:
AVX2, FMA, F16C, BMI2; aarch64: NEON). Без них модель выключается, как с `enabled = false`, а в лог
идёт `local_llm_off` с `why="cpu"` и списком недостающих флагов. Выключенная модель считается в
`complete_unavailable_total{state="off"}`, `resolve_artist` и `match_track` работают как обычно.

Движок `llm-local` идёт с `llm.local.threads` потоками и `llm.local.nice`: между резервными движками
(`nice 0`) и фоновыми (`nice 10`). Пока идёт вызов, его потоки вычитаются из бюджета, который делят
фоновые движки. OpenMP в этом движке ждёт пассивно (`OMP_WAIT_POLICY=PASSIVE`), чтобы потоки между
токенами не крутились на ядрах фоновых задач. Вызов, не уложившийся в дедлайн и 15 с запаса, движок
теряет: процесс убивается, как у некооперативных слотов.

Вызовы идут по одному. `complete` сверх `llm.local.max_in_flight` или такой, что не дождётся своей
очереди до дедлайна (по времени модели на последний законченный ответ, без ожидания в очереди),
этот воркер не берёт
(`complete_rejected_total{why="busy"}`), чтобы очередь к модели не занимала лейн.

Воркер, который не может ответить на `complete` (модель выключена, занята или её движок недоступен),
сам не отвечает, а сразу возвращает вызов в очередь (NAK без задержки), и NATS отдаёт его следующему
ждущему воркеру: `rpc_handed_on_total{method}`, строка `rpc_handed_on`. Ответ `internal` (выключена,
недоступна) или `expired` (занята) он шлёт сам в трёх случаях: доставка последняя (`max_deliver` 5,
то есть после четырёх передач), до дедлайна осталось не больше 2 с, соединению с NATS нельзя
доверять. Если ответить некому, ошибка приходит после четырёх передач, за ~10 мс. NAK, который не
ушёл, считается в `nak_failures_total`; вызов вернётся сам через `ack_wait`.

Передача идёт по кругу ждущих воркеров. Вызовы по одному всегда доходят до воркера с моделью, пока
воркеров без неё не больше четырёх. При одновременных вызовах каждая передача может попасть на
любого, и вызов, пять раз попавший к воркерам без модели, получает ошибку. Замер на NATS 2.14.9,
600 вызовов пачками по 6: один воркер без модели и один с моделью — 1 % ошибок (до правки 50 %),
два без модели и один с моделью — 14 %, четыре и один — 33 %, один без модели и два с моделью — 0.

Основное время ответа — чтение промпта, поэтому движок хранит состояние модели после прочитанных
префиксов: конец `system`, конец последнего сообщения и общее начало двух разных `system` (находит
сам). Запрос с тем же началом читает только хвост. Если `system` совпадает с уже прочитанным только
началом, движок хранит и это начало, и новый конец: следующая реплика с тем же `system` не читает
его заново, даже если прошлый вызов оборвал дедлайн. Хвост, который меняется в каждом запросе,
оставляет по концу на запрос: такие концы уходят по давности вслед за концами реплик, а общее
начало, которое они продолжают, живёт дольше них.
Вызывающему: `system` между запросами один байт в байт, всё изменчивое — в сообщениях.

Если `system` собран из разделов, вызывающий отмечает их концы в запросе:
`"system_marks": [5210, 5640]`. Это байтовые смещения в UTF-8 тексте `system`: строго по
возрастанию, каждое от 1 до длины `system` включительно, на границе символа, не больше 4
(`limits.complete.system_marks`). Поля нет или список пуст — всё как без меток. `null`, не список,
не целое, смещение внутри символа, за концом текста или не по возрастанию — `invalid_request`.
Воркер токенизирует куски между метками отдельно, поэтому метка всегда граница токена, и хранит
состояние на каждой метке, которую прочитал. Запрос, у которого `system` до метки совпадает с
прочитанным байт в байт, читает только текст после неё, уже с первого раза. С метками состояния
`system` хранятся только на метках: общее начало воркер не ищет, а конец `system` хранит, только
если он отмечен (метка равна длине `system`). Метка раньше `llm.local.eval_chunk_tokens` токенов не
хранится. Тот же `system` без меток может токенизироваться иначе, его состояния отдельные.
Перезапуск воркера теряет все состояния.

Состояния лежат в двух списках: префиксы `system` и концы реплик. Когда память под них
(`llm.local.state_cache_mib`) кончается, первыми уходят старые концы реплик, затем по давности
префиксы `system`, которые не продолжает ни одно другое состояние: общий префикс живёт дольше своих
хвостов. Только что сохранённое состояние уходит последним, так что и при памяти, занятой
префиксами, последний разговор продолжается со своей реплики. Qwen3.5 —
гибрид с рекуррентными слоями, обрезать его кэш по позиции нельзя; состояние занимает ~20 МБ плюс
~12 КБ на токен (250 токенов — 22 МБ, 1450 — 36 МБ). Префиксы `system` переживают выгрузку по
простою, концы реплик удаляются. Чтение, оборванное дедлайном внутри `system`, хранится как префикс
`system`, пока не сохранено более длинное состояние того же промпта: редкие вызовы дочитывают
`system` и через выгрузки. Состояние, которое не загрузилось, выбрасывается, и движок берёт
следующее покороче или читает промпт с нуля. Пользовательский текст не может стать служебным
токеном: ни управляющим (`<|im_end|>`), ни размеченным в файле модели (`<think>`, `<tool_call>`).

Дедлайн: перед каждым куском промпта (`llm.local.eval_chunk_tokens`) и перед каждым токеном ответа
движок сверяет время с прогнозом шага и за секунду до дедлайна отвечает `expired`, процесс не
убивается. Прогноз чтения берётся с кусков от 16 токенов (прогрев при первой загрузке читает полный
кусок; после выгрузки по простою модель загружается без прогрева, прогноз уже есть), прогноз
ответа — со всего шага вместе с выбором токена. Кусок, который по прогнозу не успевает, читается
короче, но не короче 16 токенов, так что один медленный замер исправляется следующим чтением, а не
отказывает всем вызовам. Прочитанное сохраняется, повтор того же запроса продолжает с этого места.
Грамматика, которая не пропускает ни одного токена, даёт `invalid_request`, а не падение движка.

Ошибки: промпт не помещается в окно, корень `schema` объявлен не объектом (`type` не `"object"`),
`schema` не превращается в грамматику или в JSON (глубже 255 уровней, целое шире 64 бит), в тексте
одиночный суррогат или шаблон отказал — `invalid_request`
(`complete_rejected_total{why="invalid_request"}`); ответ оборван на `max_tokens`, не JSON-объект
или не проходит `schema` — `internal` (`complete_rejected_total`); движок недоступен
(`complete_unavailable_total`) — вызов уходит другому воркеру, как описано выше. Проверка ответа не
смотрит `$ref`, `oneOf`, `allOf`, `pattern` и `format`: их держит только грамматика. На
каждый ответ идёт строка `complete_answered` с `input_tokens`, `reused_tokens`, `output_tokens`.

Окно 8192 взято под промпт api: `system` до 16 КБ, 20 реплик истории и ответ до 512 токенов — это
4100–4500 токенов, с длинными репликами (~500 символов) до 7300. Настоящий `system` api с 27
инструментами — 2218 токенов; с 20 репликами и ответом 3118.

Память движка `llm-local` с Qwen3.5-2B Q4_K_M и окном 8192: после загрузки ~350 МБ анонимной
памяти (с окном 4096 ~300 МБ) и ~1.24 ГБ страниц файла весов, которые ядро отдаёт под давлением.
Состояния префиксов добавляют до `llm.local.state_cache_mib`: `system` на 3200 токенов с репликой —
~120 МБ, с двумя такими `system` анонимной памяти ~590 МБ. После выгрузки по простою остаются
процесс (~70 МБ) и префиксы `system`, то есть до ~70 МБ + `state_cache_mib`; в замере 166 МБ.

Замер 2026-11-11 с колесом из образа, arm64-ВМ (4 vCPU, без dotprod, загрузка 3–4): чтение 16 ток/с
на 2 потоках и 26 ток/с на 4, `OMP_WAIT_POLICY=PASSIVE` ответ не замедляет. Промпт api на 3566
токенов с нуля читается 285 с, следующая реплика с тем же `system` — 15 с; настоящий `system` api —
193 с и 7 с. На такой машине первый запрос с новым `system` не влезает в окно 30 с: каждый `expired`
сохраняет прочитанное, и через несколько запросов `system` прочитан. На x86 замера нет.

Выбор модели, 2026-11-11: 4 потока, arm64-ВМ, llama.cpp, собранный с dotprod (не колесо образа),
промпт персонажа ~1600 токенов с 34 инструментами, ответ ~45 токенов. Машина делилась с другими
задачами, числа — лучшие из прогонов. «С нуля» — первый запрос с новым `system`, «повторный» — тот
же `system` и новая реплика. «Действия» — сколько из 15 реплик RU/EN дали ровно нужные команды,

### Голос

`speak.rpc.say` озвучивает строку. Слот `tts` держит процесс `scd-qwen` с одним голосом, на CPU
или на первой CUDA-карте (`tts.device`).
Холодная загрузка голоса - 6-7 с, смена голоса - полная выгрузка и такая же загрузка. Ответ - Ogg
Opus, моно, 48 кбит/с, в base64 прямо в ответе, кодирует `ffmpeg` из образа. Текст в лог не
попадает, только длина. Лейн есть в профилях `cpu-tts` и `gpu-tts`.

Строку берут доверенные воркеры и публичные ноды через мост. Публичная нода, которая ждёт строку,
получает её раньше доверенного воркера: так задаёт `lanes.speak.priority_group` в контракте.
Доверенный воркер называет группу и свой приоритет в каждом pull. Консьюмер без группы он
обслуживает так же (так лейн выглядит, пока `jobs` не выкачен с группой), другая группа или
политика - расхождение. Порядок выкатки: сначала воркеры, потом `jobs`. Воркер прежней версии
на консьюмере с группой получает отказ 400 на каждый pull.

Неизвестный голос или текст длиннее `limits.say.text_chars` из контракта - `invalid_request`,
движок не вызывается. Доставка одна (`max_deliver = 1`): ошибка сразу уходит ответом.

| Ключ | По умолчанию | Что задаёт |
|---|---|---|
| `tts.base_urls` | `["https://storage.scnative.dev/voice-models"]` | адреса хранилища по порядку; хосту - `WORKER__TTS__BASE_URLS='["https://a/voice-models", "https://b/voice-models"]'` |
| `tts.download_mib_s` | 4 | потолок скорости `fetch-models` для файлов голоса, общий на все файлы и адреса; 0 - без потолка |
| `tts.device` | `cpu` | `cpu` или `cuda` |
| `tts.idle_unload_s` | 600 | простой, после которого процесс голоса останавливается |
| `tts.engine`, `tts.codec`, `tts.voices` | | файлы и их sha256, пути от `SCD_TTS_MODELS_PATH` (в образе `/models/tts`) |
| `tts.engine.cuda_files` | `libggml-cuda.so` | файлы движка, которые качаются только при `tts.device = "cuda"` |

Процесс с голосом на CPU держит ~3.8 ГБ, хосту `cpu-tts` нужна память от 6 ГБ. Потоки движку
задаёт воркер через `SCD_QWEN_THREADS`: половина логических CPU, но не больше маски CPU процесса и
квоты cgroup (`cpu.max`, в v1 `cpu.cfs_quota_us`). Движок без этой переменной берёт половину CPU
хоста и квоту не видит.

На `cuda` движок грузит `libggml-cuda.so` из своей папки, а `libcudart.so.12`, `libcublas.so.12` и
`libcublasLt.so.12` - из колёс `nvidia-cuda-runtime-cu12` и `nvidia-cublas-cu12` образа `:gpu`:
воркер ставит их папки в `LD_LIBRARY_PATH` процесса голоса после папки движка. В `:gpu-cuda13`
этих библиотек нет, CUDA-бэкенд не загрузится и голос не стартует. На ноде `gpu-tts` кроме голоса
работают только сам воркер и `ffmpeg` на каждый ответ. Видеопамять голоса не замерена: веса - это
говорящая модель 1.18 ГБ и кодек 0.29 ГБ, рабочие буферы движок растит до худшего случая и не
отдаёт.

## Образ

Один `docker/Dockerfile`, сборка torch выбирается `FLAVOR`:

| Тег | `FLAVOR` | torch | Драйвер |
|---|---|---|---|
| `:gpu`, `:gpu-cuda12`, `:X.Y.Z-gpu` | `cu126` | 2.13, Pascal–Ada | ≥ R560 |
| `:gpu-cuda13`, `:X.Y.Z-gpu-cuda13` | `cu130` | 2.14, Turing+ и Blackwell | ≥ R580 |
| `:cpu`, `:X.Y.Z-cpu` | `cpu` | 2.13 | — |

`:gpu-cuda13` проверен 2026-10-15 на RTX 5060 Ti (sm_120, драйвер 595.84, CUDA 13.2), образ
9.8.19: models-тесты 47 passed, 3 skipped. Blackwell (sm_100, sm_120) идёт только на `:gpu-cuda13`,
Pascal и Volta (V100) остаются на `:gpu`. CUDA приезжает колёсами `nvidia-*`, драйвер — с хоста.
llama.cpp для локальной модели во всех трёх сборках один: колесо `llama-cpp-python` под CPU из
`uv.lock`; на x86_64 ему нужен процессор с AVX2, FMA, F16C и BMI2 (Haswell, Zen и новее).

```bash
docker build -f docker/Dockerfile --build-arg FLAVOR=cu126 -t worker:gpu .
podman build --format docker -f docker/Dockerfile --build-arg FLAVOR=cu126 -t worker:gpu .
```

`podman build` без `--format docker` молча выбрасывает `HEALTHCHECK`.

Контейнер: пользователь uid 10001, `read_only: true`, tmpfs `/tmp` и `/run/worker:mode=1777`, тома
`models:/models` и `work:/work`, `shm_size: 4g`, `stop_grace_period: 90s`, секреты через `env_file`,
один контейнер на GPU. У каждого сервиса воркера на хосте свой том `/work`: воркер при старте
очищает `/work` целиком и сотрёт папки задач другого сервиса на том же томе. Podman монтирует
tmpfs без `mode` как `root 0755` (кроме `/tmp`), и воркер не может записать
`/run/worker/health.json`: процесс выходит с кодом 1 сразу после старта.

### Веса

Веса в образ не входят. Перед первым запуском:

```bash
docker compose run --rm -e HF_HUB_OFFLINE=0 worker fetch-models --profile gpu-24
```

Команда качает ревизии из конфига только для слотов включённых лейнов профиля (с резервами),
fastText `lid.176.bin`, чекпойнт сепаратора и GGUF локальной модели сверяет по sha256; GGUF с
другим хэшем удаляется. `--profile cpu-tts` качает движок и голоса (~2.7 ГБ) в
`SCD_TTS_MODELS_PATH` и сверяет их по sha256. Каждый файл берётся с первого адреса `tts.base_urls`;
если адрес не отдал его после всех повторов, качается со следующего, докачивая уже полученную часть.
Все файлы голоса вместе идут не быстрее `tts.download_mib_s`. Код выхода: 0 — всё скачано,
1 — часть не скачалась (каждая ошибка в строке `model_fetch_failed`), 78 — ошибка конфига.
